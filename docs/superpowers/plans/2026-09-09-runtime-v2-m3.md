# Runtime v2 M3 Implementation Plan

> **For agentic workers:** Use superpowers:executing-plans to implement this plan task by task, with independent review before delivery. Steps use checkbox syntax for tracking.

**Goal:** Prove foreground/detached effect recovery and submit durable one-shot and fixed-interval work through the existing runtime.

**Architecture:** Keep M2's single Store connection, Runtime worker, checkpoints, and Executor. Add schedules and occurrence reservations to Store; use the same private submission operation inside their transaction. A small Scheduler polls independently of the worker, so slow model/tool work cannot block reservations or approval expiry.

**Tech Stack:** Existing locked Python >=3.11, sqlite3, Pydantic, FastAPI, Typer, pytest, Docker CLI. No new dependencies.

**Spec:** [September 9 design](../specs/2026-09-09-runtime-v2-design.md), [M3 roadmap](2026-09-09-runtime-v2-roadmap.md), [M2 plan](2026-09-09-runtime-v2-m2.md), [M2 report](../../reports/2026-09-09-runtime-v2-m2.md), [M2 results](../../reports/2026-09-09-runtime-v2-m2-results.json).

## Global constraints

- Python >=3.11; CI on Python 3.11 and 3.13; initial runtime support is macOS and Linux.
- One installable package at src/hyperclaw and one CLI entrypoint: hyperclaw.
- One daemon owns each runtime root, its SQLite connection, model requests, and tool processes.
- Default runtime root is ~/.hyperclaw-v2; default HTTP listener is 127.0.0.1:8011.
- Default model is qwen3.8:27b-mlx at http://127.0.0.1:11434; no cloud fallback or automatic model download.
- Existing ~/.hyperclaw data, .engram, other worktrees, and running services are outside the refactor's mutation scope.
- No old HTTP routes, import paths, environment aliases, database formats, or dashboard feature parity are required.
- Persistent side effects must pass through the execution policy and have a recorded invocation.
- Client disconnect does not cancel a run; cancellation is an explicit operation.
- Unknown tool outcomes are recorded as uncertain and are never automatically retried.
- Offline tests use temporary roots and loopback fixtures; real Ollama and Docker tests require explicit selection.
- Imported skills, retrieved text, and model output cannot grant execution authority.

## Actual M2 baseline and decisions

Worktree `.worktrees/runtime-refactor`, branch `refactor/runtime-v2`, HEAD `4727861`; implementation `b11a34c`. M2 already supports `chat --detach`, durable tool checkpoints, invocation receipts, and startup reconciliation before worker creation. Store schema is version 2. A running run is terminalized at startup; it is never revived. Waiting approval survives and an approval decision requeues the exact checkpoint.

M3 first proves these paths with real child-process SIGKILL tests and real HTTP/model transport. Test-only launchers wrap named persistence/effect boundaries, publish a barrier file, and wait for the parent to kill that owned process. Production code gets no fault-injection environment variables or hooks. The deterministic matrix uses real workspace mutations; the explicitly selected Docker matrix uses real owned containers.

| Kill boundary | Durable evidence | Recovery outcome |
| --- | --- | --- |
| Before invocation creation, after tool checkpoint | Pending call; no invocation/effect | Run interrupted; no dispatch after restart |
| After invocation creation, before dispatch marking | Prepared intent; no effect | Invocation interrupted with never-dispatched evidence; run interrupted |
| After dispatch, before receipt | Running intent; effect may have happened | Host mutation uncertain; Docker inspects/stops owned container, records interrupted if termination established or uncertain if unavailable; no replay |
| After receipt commit, before checkpoint/result continuation | Immutable receipt and artifact evidence | Receipt retained; run interrupted because answer incomplete; verification retained; no effect replay |

An additional host dispatch-marker gap is conservatively uncertain even if no file was yet changed. Completed and uncertain receipts remain immutable. Repeated startup must not create another receipt or terminal event. An explicit retry cannot target an uncertain run. A known completed tool effect does not make an incomplete model response successful.

Schedules use operator-supplied `id` for idempotent creation and immutable creation payload comparison. `ScheduleRequest` has `id`, `session_id`, `generation`, `input`, `next_due_at`, optional positive integer `interval_seconds`, and the existing tool allowlist. It validates the input via RunRequest. Aware instants normalize to UTC with fixed microsecond precision; naive times fail. Schedule times are bounded to 1970–9998 and interval seconds to 1–31,536,000 to keep arithmetic representable. Overflow of a future occurrence completes the schedule after the last representable occurrence.

Each reservation has primary key `(schedule_id, nominal_due_at)` and unique `run_id`. The earliest pending nominal due instant is retained during downtime or session occupancy. At successful enqueue, coalesce all missed intervals into that one run and advance from the nominal instant to the first instant strictly after tick time. No drift to `now + interval`; one-shots become completed. A queued/cancelled/failed/interrupted occurrence is consumed and never recreated. Request IDs use a reserved `schedule:` namespace to prevent manual submission collisions. Run events include schedule ID and nominal instant.

A generation mismatch pauses the schedule, including immediately on session reset. It retains its pending instant. The operator must explicitly retarget with the expected existing generation and selected current generation before polling can resume; completed schedules cannot be retargeted. Pausing does not cancel already queued runs. A prior uncertain scheduled run pauses future occurrences as `uncertain_effect`; M3 has no automatic uncertainty reconciliation or resumption. Normal explicit interval occurrences after known outcomes are distinct runs, not invocation retries.

## Files and interfaces

- `execution/__init__.py`, `store.py`: settle never-dispatched active intents and preserve recovered receipt verification.
- `tests/support/recovery_daemon.py`: test-only process barriers; `tests/support/process.py`: optional test launcher.
- `tests/integration/test_recovery.py`, `tests/live/test_recovery_docker.py`: process kill/effect/replay evidence, foreground/detached workflows, queue/approval concurrency and responsiveness.
- `contracts.py`: `ScheduleRequest`, `Schedule`, `ScheduleOccurrence`, `ScheduleRetarget`; UTC normalization and bounded input.
- `store.py`: additive v3 migration; `create_schedule(request)->Schedule`, `get_schedule(id)->Schedule`, `schedules()->list[Schedule]`, `schedule_occurrences(id)->list[ScheduleOccurrence]`, `pause_schedule(id)->Schedule`, `retarget_schedule(id, expected_generation, generation)->Schedule`, `tick_schedules(now:datetime)->list[str]`. Shared `_submit(request, schedule=None)->Run` contains acceptance SQL and runs only inside the caller's transaction.
- `scheduling.py`: `Scheduler(store)` and `tick(now:datetime)->list[str]`; datetime arithmetic stays at this boundary, durable transitions in Store.
- `runtime.py`: operator schedule methods and owned maintenance task; no second execution loop. Maintenance failures make acceptance unavailable and are reported by health.
- `api.py`: authenticated create/list/get/pause/retarget/occurrences routes under `/v1/schedules`; health reflects worker/maintenance availability.
- `cli.py`: `schedule create/list/inspect/pause/retarget/occurrences`; HTTP only. Creation accepts ID, session, due UTC instant, interval and tools. Current generation is fetched explicitly.
- `tests/unit/test_scheduling.py`, `tests/integration/test_scheduling.py`, CLI tests: transactional and public-path evidence.
- README/testing docs, roadmap/design status, M3 acceptance Markdown/JSON: actual shipped scope and commands.
