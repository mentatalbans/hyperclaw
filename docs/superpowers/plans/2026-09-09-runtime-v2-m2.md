# Runtime v2 M2 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Give the existing M1 daemon scoped file tools and owned Docker commands with durable approvals, non-replayed receipts, verified cancellation, complete tool-call blocks, and image input.

**Architecture:** Extend M1's single Store connection and single Runtime worker. An Executor records intent before effects, checks operator authority immediately before dispatch, and owns a descriptor-scoped Workspace plus a Docker backend. Runtime checkpoints the actual model conversation and pending calls before dispatch/approval; approval resumes those calls without model regeneration.

**Tech Stack:** Existing locked Python >=3.11, sqlite3, Pydantic, httpx, FastAPI, Typer, pytest; Docker CLI with argument arrays, no host shell.

**Spec:** [September 9 design](../specs/2026-09-09-runtime-v2-design.md), [roadmap M2](2026-09-09-runtime-v2-roadmap.md), [M1 acceptance](../../reports/2026-09-09-runtime-v2-m1.md).

## Global Constraints

- Python >=3.11; CI on Python 3.11 and 3.13; initial runtime support is macOS and Linux.
- One installable package at src/hyperclaw and one CLI entrypoint: hyperclaw.
- One daemon owns each runtime root, its SQLite connection, model requests, and tool processes.
- Default runtime root is ~/.hyperclaw-v2; default HTTP listener is 127.0.0.1:8011.
- Default model is qwen3.8:27b-mlx at http://127.0.0.1:11434; no cloud fallback or automatic model download.
- Existing ~/.hyperclaw data, .engram, other worktrees, and running services are outside the refactor's mutation scope.
- No old HTTP routes, import paths, environment aliases, database formats, or dashboard feature parity are required.
- Persistent side effects must pass through the execution policy and have a recorded invocation.
- Client disconnect does not cancel a run; cancellation is an explicit operation.
- Unknown tool outcomes are recorded as uncertain and are never automatically retried.
- Offline tests use temporary roots and loopback fixtures; real Ollama and Docker tests require explicit selection.
- Imported skills, retrieved text, and model output cannot grant execution authority.

## Actual M1 baseline and decisions

Work only in `.worktrees/runtime-refactor`, branch `refactor/runtime-v2`, starting at `7fa9dee`. Baseline: 88 offline tests passed, 3 live deselected. M1 has `Message.content: str`, no tool/image parsing, one `Runtime._execute` model request, and schema version 1. `Store._call` already settles cancelled transactions. Keep these ownership and settlement properties. Extend the schema using a backed-up transactional migration; do not edit existing personal databases.

M2 uses one explicitly selected workspace per daemon: `workspace_path` in configuration, with an empty default selecting `root/workspace`. It must be a real directory, cannot be the operator home, runtime root, or an ancestor of either, and is never inferred from cwd. Workspace identity includes its canonical path and device/inode. Operator grants are scoped to that identity; execution and write are independent. Per-run `tools` is an allowlist; default is the five admitted file/command tools. An offered effect tool may require approval; offering never grants authority.

M2 provides `workspace_read`, `workspace_list`, `workspace_search`, `workspace_write`, and `command`. Paths are relative; write requires an existing parent directory. Commands accept an argv list, never a host shell string; callers may explicitly request `/bin/sh -c` *inside* Docker. `workspace_write` and command artifact checks accept an expected SHA-256; observed file hashes become artifact records, and mismatches fail the run. A command without a write grant gets a read-only workspace even when its exact execution was approved.

Approvals bind invocation ID, canonical argument hash, schema/effective-policy hash, and workspace identity. A positive decision authorizes exactly that invocation. Durable workspace grants are a separate operator operation. Pending approvals expire after 24 hours. Store persists full checkpoint messages, pending calls, round count, repeated-call counts, and elapsed execution time. Active time excludes queued/approval waits. At an abrupt crash, conservatively charge the running interval until recovery (uncertain crash time may exhaust the remaining budget); never give a restarted invocation a fresh budget.

Use at most 12 model rounds, at most 3 identical name/argument requests per run, at most 16 calls per round, a 64 KiB text context, opt-in attachment context up to 8 MiB, 64 KiB tool output, and tool deadlines at most 60 seconds and the remaining run budget. Each model request still uses the configured 120-second deadline. No completed or uncertain invocation re-executes.

## Files and interfaces

- `contracts.py`: `ToolCall(id, name, arguments)`, `ToolReceipt(invocation_id, status, output, artifacts, evidence)`, `Artifact(path, sha256, size_bytes)`, `Checkpoint(messages, pending_calls, round_count, call_counts, elapsed_s)`; structured `Message.content`, validated images, `RunRequest.tools/images/context_bytes`, run verification and waiting/uncertain status.
- `store.py`: migration and all durable grants/invocations/approvals/artifacts/checkpoints; keep SQL private and one executor/connection.
- `execution/docker.py`: only container and docker-client process ownership. `DockerBackend(installation_id, workspace, image=TOOL_IMAGE)`; `create(invocation_id, argv, writable)->str`, `start(container_id)`, `wait(container_id, timeout_s, output_limit)->DockerResult`, `terminate(container_id)->DockerResult`, `owned()->list[dict]`, `remove(container_id)`. `DockerResult` holds status, output, exit_code, terminated, truncated; backend unavailability raises `DockerUnavailable`. All methods async. Labels contain installation and invocation IDs. Executor persists ID between create and start.
- `execution/workspace.py`: `Workspace(path)` with `identity`, `read(path, limit=65536)->str`, `list(path='.')->list[str]`, `search(query, path='.')->list[dict]`, `write(path, content, expected_sha256=None)->dict`, `inspect(path, expected_sha256=None)->dict`, `close()`. Result dictionaries contain `path, sha256, size_bytes, verified`; mismatches return `verified=False`. File methods are synchronous and bounded; Executor runs them in a settled thread operation.
- `execution/policy.py`: tool schemas/argument validation, effect/deadline/output declarations and deterministic policy hash. Default reads; separate write/execute grants.
- `execution/__init__.py`: `Executor.invoke(run_id, call)->ToolReceipt`, `cancel(run_id)->None`, `reconcile()->list[ToolReceipt]`; raises `ApprovalRequired` after durable checkpoint/approval state, never executes the pending effect. Runtime owns and closes Executor.
- `ollama.py`: `stream(messages, system='', tools=None)` emits existing text/thinking/usage plus complete `tool_call` events after block validation. Finish includes complete assistant `content` and `stop_reason` so the Runtime can preserve thinking/signatures/tool IDs and exact grouping.
- `runtime.py`: loop/checkpoint/approvals, active budgets, startup reconciliation before claiming queued work, tool-result grouping and verification. Public operator methods `approvals`, `decide_approval`, `grant`, `receipts`.
- `api.py`, `cli.py`: authenticated operator controls, image submission, inspection. No storage writes in CLI.
- `containers/tool-runner/Dockerfile`: versioned resolved digest for Python/basic filesystem tools; hardened invocation controls are in DockerBackend.
- `tests/integration/test_execution.py`, `tests/integration/test_tools_runtime.py`, `tests/unit/test_execution_store.py`, `tests/unit/test_workspace.py`, `tests/unit/test_tool_transport.py`, `tests/live/test_docker.py`, `tests/live/test_ollama.py`: acceptance evidence.
