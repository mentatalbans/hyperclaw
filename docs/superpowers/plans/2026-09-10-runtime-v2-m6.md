# Runtime v2 M6 Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Make the existing local runtime usable through a small web interface and an optional, durable Telegram polling adapter, then verify the complete M1–M6 workflow.

**Architecture:** The web page consumes the authenticated loopback HTTP API. Telegram normalizes authorized updates into the same Runtime.submit contract; Store owns session mappings, update deduplication and delivery records. API lifespan owns the optional adapter alongside the existing runtime. No second orchestrator or service is introduced.

**Tech Stack:** Python 3.11+, SQLite/Store, FastAPI, HTTPX, standard HTML/CSS/JavaScript; optional Playwright browser-test extra. Telegram uses the official HTTPS Bot API directly through HTTPX, with no additional runtime dependency.

**Spec:** [Approved design](../specs/2026-09-09-runtime-v2-design.md), [approved M6 roadmap](2026-09-09-runtime-v2-roadmap.md), [M5 acceptance](../../reports/2026-09-10-runtime-v2-m5.md). The user approved M6 after its scope was presented. Base `c3037db829f34d3c30f12711042619d77deeddbe`, existing isolated worktree on `refactor/runtime-v2`. Continue implementation, review, verification and local commits; retain the branch/worktree. Shared-service adoption, real Telegram messages, push and merge are outside this delivery.

## Global Constraints

- Python 3.11+ on macOS/Linux; one Python package owns all advertised behavior.
- Root selection is --root, then HYPERCLAW_ROOT, then ~/.hyperclaw-v2. No dotenv loading, import-time mutation, or legacy provider environment probing.
- Web authentication uses the bearer header, with no token in a URL or persistent browser storage. Event streaming uses authenticated fetch.
- Telegram requires explicit bot credentials and allowed chat/sender pairs, checked before attachment downloads. Map (bot identity, chat, topic, sender) to one session ID in Store. Deduplicate by update ID; persist delivery status. A Telegram send with an unknown outcome is visible and not blindly resent. Omit webhooks and additional channels.
- Reuse existing Runtime, Store, grants, exact approval hashes, context limits, receipt/effect semantics and model selection. Do not make adapters alternative tool-execution paths.
- Default startup, CLI help and doctor remain independent of Telegram/network/browser/MCP availability. Enabling Telegram is explicit. Credentials never appear in config dumps, error messages, URLs shown to users, evidence, or logs.
- Keep browser assets and dependencies local; no external fonts, CDNs, analytics, frameworks, package managers or browser downloads during ordinary startup.
- Existing locked dependency versions stay unchanged unless the new optional test dependency requires a justified change. No model download, cloud fallback, personal-root adoption, shared-service restart, or real Telegram send during this task.
- Preserve all previous acceptance evidence and carried M4/M5 limitations, including imperfect model citation line numbers. Full deterministic tests at milestone boundaries; live/Docker/browser gates are explicit and reported with actual exclusions, runtime versions, input hashes and outcomes.

## Detailed decisions

This plan concretizes the existing design rather than reopening it. Web is a static client served by the same daemon: a token-connect screen, session list, conversation/run area, explicit reconnect/cancel/reset controls, and exact-invocation approvals and receipts. A separate front-end service would complicate authentication/deployment; an additional UI framework would add a build toolchain without a requirement. Use responsive CSS, readable system fonts, restrained color, accessible labels/focus/keyboard behavior, visible connection/run status and plain text rendering of untrusted content.

Telegram is a disabled-by-default part of the daemon lifespan, not a second CLI-owned runtime. Add `telegram_enabled = false` and `telegram_allowed_pairs = []` (canonical `"CHAT_ID:SENDER_ID"` strings; signed nonzero chat IDs and positive sender IDs, strict decimal values within 52-bit IDs, unique pairs). When enabled, read the fixed private `root/telegram-token` file with bounded descriptor-based nonblocking/no-follow regular-file checks, 0600 permissions and no hardlinks. Do not put the secret itself in Settings. Authenticate bot identity with getMe, reject an existing webhook without modifying it, and persist state under that stable bot ID. Enabled startup failures have sanitized errors; disabled startup performs no Telegram IO. Poll failures expose adapter status and bounded backoff while ordinary runtime work stays usable.

M6 accepts ordinary text and one Telegram photo with an optional caption. Reject unsupported updates, bot/sender_chat/channel/anonymous senders and unsupported attachments without interpreting them as model input. Allowed pairs are required in private chats and groups alike; topic/thread IDs participate in routing. Telegram does not offer grant/admit/approval administration. Runtime's default nine tools remain subject to operator policy; no MCP or skills are auto-selected. Waiting approvals direct the operator to the local web/CLI using the run ID.

Attachment retrieval is authorized before getFile and before download. Select a bounded photo; cap downloaded bytes at 4 MiB, independently of declared file_size. Use only api.telegram.org HTTPS and validated relative file paths returned by getFile; reject traversal, absolute URLs, encoded separators, query/fragment and redirects. Verify content as an existing ImageAttachment and submit with an explicit 8 MiB context budget. Ordinary text retains the 64 KiB budget. Poll JSON is capped at 1 MiB, getUpdates requests at 25 updates with a 20-second long poll and bounded HTTP deadlines. No unbounded materialization or arbitrary download URL exists.

Every authorized update is durably reserved before asynchronous work. Preserve the chosen session generation and stable request ID `telegram:<bot_id>:<update_id>` with normalized request data before Runtime.submit. An accepted run must be discoverable after a crash between submit and binding the update. Reconcile that exact (session, generation, request_id), rather than creating another run or using a newer generation. Handle session-busy and stale-generation outcomes explicitly. Persist ignored/rejected update IDs too, without retaining unauthorized message text; only advance the polling offset after durable intake. Outbound delivery is independent of long-running model work so polling and local cancellation remain responsive.

Outgoing messages use plain text, at most 3,500 UTF-16 code units including any truncation note and run ID. Reply to the originating message/thread. Persist each delivery phase (approval notice or terminal result) under a unique (bot, update, phase) key. Commit `sending` before HTTP; record a validated successful message ID as `sent`. Explicit rejection is `failed`; an ambiguous transport/response or restart with `sending` is `uncertain`. Neither failed nor uncertain sends are silently retried. Expose recent delivery records and sanitized adapter status through authenticated GET /v1/telegram and `hyperclaw telegram status`. No shared Telegram state is changed by tests.
