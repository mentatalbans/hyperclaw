# HyperClaw implementation evidence

Scope: checkout `feat/consolidate-ollama`, commit `ad32fa2`, inspected September 9, 2026. **Observed** means source inspection; **recorded** means an existing test report; **inference** means an architectural conclusion. No services, model calls, or tests were run for this note. Private runtime data and `.engram` were not inspected.

HyperClaw has a credible local assistant runtime with durable conversations, bounded tool use, provider routing, and meaningful regression tests. Its wider swarm, connector, skills, and learning modules should be evaluated separately: they do not all share that runtime or its verification evidence.

| Area | Observed implementation | Comparison implication / limitation |
| --- | --- | --- |
| Interactive runtime | HTTP, terminal, agent adapter, and Telegram polling converge on `Orchestrator`; startup owns three task workers and explicitly enabled background services. Per-session locks serialize turns. Streaming cleanup persists received assistant text in `finally`.[1] | A substantial consolidation strength. The shared transport supports streamed text/thinking separation; tool rounds use completed model responses, so tool-enabled turns do not provide token-by-token generation through `ToolLoop`.[1][2] |
| Providers and Ollama | The registry declares six provider entries: Ollama, Anthropic, two generic OpenAI-compatible configurations, ChatJimmy, and native OpenAI. Candidate ladders filter declared capabilities and configured environment requirements. Ollama uses `/v1/messages`; local setup probes installed model names, selects Ollama, enables tools, and disables database, Telegram, and scheduler by default.[2] | Explicit provider selection prevents canonical inference from falling through to another service. Capabilities are provider declarations rather than per-model discovery in normal routing. Auxiliary `core/providers/llm.py` contains 17 concrete provider classes; their existence does not establish interactive integration or live compatibility. Other workflows still instantiate their own clients.[2][7] |
| Sessions and memory durability | Session filenames use SHA-256 identifiers; JSON writes use temporary files, flush/fsync, and atomic replacement. Database saves use transactions, stable message IDs, and advisory locking when finding/creating conversations. Reset persists an empty state before changing cache. Memory writes and deletion are durable; legacy imports preserve originals.[3] | Strong persistence foundation, with recorded process-restart, collision, reset, transactional import, and cancellation tests. Locks and caches remain process-local; this evidence does not establish multi-worker coordination. File history retains 100 messages; prompts use the last 20. Reset clears conversation history, not the separately stored memories.[1][3] |
| Memory retrieval and scope | Active `MemoryManager` initializes `_embeddings_client=None`; `_get_embedding()` returns `None`. Local recall scores query-word substrings; database fallback uses whole-query `ILIKE`. Explicit memory tools share canonical storage and filter reads/deletes by session, while `memory_store` creates a global record.[4] | Semantic retrieval is not implemented in the active manager despite separate vector/provider modules. Automatic recall fetches ten candidates before filtering session visibility, potentially crowding out relevant own-session records. Automatic memory extraction is keyword-triggered, truncated exchange text. Shared workspace context and explicit global memories mean history isolation is not a general tenant boundary.[1][4] |
| Tools, approval, isolation | Terminal loads the static 87-tool catalog. HTTP defaults to a small core computer-tool subset when tools are enabled. `ToolLoop` restricts offered names, caps rounds at 12, limits a turn to 600 seconds, bounds individual tools, and stops repeated identical calls. Host shell/file tools execute directly; synchronous tools run in threads.[5] | Useful execution controls, but no general approval broker or OS isolation boundary is present in this dispatch path. Timeouts can leave a worker thread running; the loop ends to avoid blind retries. HyperShield policy/guard/audit classes exist and have unit tests, but are not injected into canonical tool execution. Optional connector capability checks are not equivalent to approval enforcement.[5] |
| Channels and access boundaries | Canonical Telegram polling is allowlist-based, denies empty allowlists, partitions sessions by tenant/chat, and checks authorization before attachment downloads. Its webhook checks a shared secret and chat allowlist. Server defaults to loopback; application setup has CORS middleware and ordinary HTTP handlers with caller-supplied session IDs.[6] | Suitable evidence for a trusted local operator, not an authenticated multi-user gateway. No common HTTP authentication middleware/dependency was found. Polling uses `telegram:{tenant}:{chat}`, but webhook uses `telegram_{chat}`: those transports do not resume the same history. Additional messaging connectors use a separate Nexus-oriented gateway and lack equivalent live validation.[6] |
| Tasks and recovery | `AgentCoordinator` routes using keyword/domain scoring, queues in `asyncio.Queue`, and holds task records and execution locks in dictionaries. Competing calls share one terminal outcome. Execution is one `model_router.call`; coordination plans, runs up to three subtasks, and synthesizes results.[7] | Recorded tests demonstrate same-process deduplication and cancellation handling, not durable task recovery. No task checkpoint/replay store is wired here, and queued specialists do not inherit the interactive tool loop. Separate HyperState/UCB1/Nexus modules provide persistence and routing experiments through another CLI path.[7] |
| Scheduler and extensibility | Scheduler registers five fixed APScheduler jobs: heartbeat, morning brief, restart, memory consolidation, and all-hands. It creates no persistent job store; consolidation imports `memory_store` from an external user directory. Skills are core definitions plus JSON registry/proposals, with model-reported safety scores controlling activation.[8] | Scheduling is built-in automation rather than a verified durable user-job service. Source search found no native MCP, ACP, or `SKILL.md` loader in Python/TOML implementation. The custom skills registry is not evidence of compatibility with standard skill packages; `ClaudeCodeSubagent` is a generated-Python subprocess loop, not a Claude Code/ACP client.[8] |
| Observability and evaluation | Canonical inference tracks served provider/model, token usage, latency on completions, and configured price estimates. Runtime status and model/cost endpoints expose this state. Separate HyperState records experiments; its certifier checks nonempty result/test trace and a supplied certified flag.[9] | Usage totals are in-memory; daily budget changes routing rather than enforcing a hard cap. No common distributed trace or production quality-evaluation pipeline was found. `hyperclaw/prometheus.py` is a memory-consolidation agent, not a Prometheus metrics exporter. Existing smoke tests check contracts, not broad autonomous-task quality.[9] |

The strongest recorded evidence is the retained September 9 all-run: **651 passed, 1 skipped, 8 warnings**, Python 3.11.13, including five live scenarios on Ollama 0.33.3 / `qwen3.8:27b-mlx`. Those scenarios verify plain response/provenance, streaming/accounting, restart/isolation/reset, actual memory tool results reaching the model, and synthetic image interpretation. A separate Python 3.13.5 full run records 646 passed and one skip.[10]

Coverage qualifies the breadth: the all-run measures **33.3% of statements and 24.9% of branches** across its selected packages (31.6% combined). Combined coverage is 89% for the memory manager, 83% for the coordinator, 0% for scheduler/skills, and 1% for the large TUI implementation. The battery explicitly excludes pgvector similarity/embedding quality and does not prove live external connector behavior.[10] These are past observations, not fresh validation of every module.
