# Claw interoperability and execution boundaries

Research date: **2026-09-09**. Primary sources only. MCP citations use the published **2026-07-28** revision; ACP uses stable **v1**, with v2 explicitly distinguished as draft. OpenClaw pages and SDK `main` documentation are rolling sources, retrieved on the research date: their claims are documentation evidence, not proof that an older installed release behaves identically. This is research only; no integration was installed or exercised.

**Recommendation (engineering judgment):** retain HyperClaw's Python/Ollama core and first evaluate a narrow MCP client adapter against named, useful integrations. Add ACP when an editor must drive HyperClaw or HyperClaw must supervise an external coding harness. Consider A2A when there is a concrete independently operated agent service to delegate to. These are separate product needs, not successive maturity levels.

## Protocols and version status

**MCP provides tools and context.** Hosts contain clients that connect to servers exposing tools, resources, and prompts. It standardizes JSON-RPC communication; it does not implement the host's consent, access-control, or execution sandbox. The normative overview explicitly treats tool descriptions and annotations as untrusted unless their server is trusted. [Published specification, 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28).

The current `latest` endpoint resolves to **2026-07-28**, superseding 2025-11-25. This release removes the initialization handshake and protocol-level sessions, including `Mcp-Session-Id`; requests carry version/capability metadata, and `server/discover` advertises server capabilities. Tasks moved to an opt-in extension. Roots, sampling, logging, and legacy HTTP+SSE are deprecated. An integration copied from 2025 examples therefore needs explicit compatibility handling. [Current revision changes](https://modelcontextprotocol.io/specification/2026-07-28/changelog), [release announcement, 2026-07-28](https://blog.modelcontextprotocol.io/posts/2026-07-28/).

**ACP provides an agent/client interaction lifecycle.** Stable v1 defines initialization, authentication, session creation/loading, prompts, streaming updates, cancellation, and client-facing filesystem/terminal capabilities. Session setup can carry MCP server definitions: ACP and MCP can compose. ACP reports tool activity while the agent remains responsible for execution. Its permission method is optional for agents; clients can apply user settings automatically. A compatible wire format consequently does not prove every tool execution was approved. [ACP v1 overview](https://agentclientprotocol.com/protocol/v1/overview), [session setup](https://agentclientprotocol.com/protocol/v1/session-setup), [tool calls and permission requests](https://agentclientprotocol.com/protocol/v1/tool-calls).

ACP's defined practical transport is subprocess stdio; Streamable HTTP remains a draft proposal. **ACP v2**, announced **2026-07-20**, remains draft and changes prompt lifecycle, updates, diffs, and permission requests. Its maintainers advise version negotiation plus feature flags and retaining v1 compatibility. Do not conflate published v2 documentation with a stable production contract. [v1 transports](https://agentclientprotocol.com/protocol/v1/transports), [v2 draft announcement](https://agentclientprotocol.com/announcements/acp-v2-draft).

**A2A provides communication with independent agent services.** Its latest released specification is **1.0.0**, with capability discovery through Agent Cards, messages, tasks, artifacts, and asynchronous updates. It supports collaboration without access to another agent's internal tools or memory. Authorization checks and resource scoping remain implementation responsibilities; an `AUTH_REQUIRED` task state does not itself grant authority. This is useful for service-to-service delegation, beyond the editor/harness relationship emphasized by ACP. OpenClaw documents an included A2A v1.0 channel plugin. [Released A2A specification](https://a2a-protocol.org/v1.0.0/specification/), [current release selector](https://a2a-protocol.org/latest/specification/), [OpenClaw A2A inventory](https://docs.openclaw.ai/plugins/reference/a2a).

## MCP authorization and security implications

MCP authorization is optional overall. The HTTP authorization profile uses OAuth; stdio implementations instead obtain credentials from their environment. Current requirements include protected-resource discovery, audience-bound tokens, per-request authorization, and resource indicators. Client ID Metadata Documents are preferred; Dynamic Client Registration is retained but deprecated. The profile still references the OAuth 2.1 and client-metadata **IETF drafts**, so published MCP status should not be mistaken for final RFC status of every dependency. [Authorization, 2026-07-28](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization).

Clients must verify PKCE support, protect tokens, and enforce the specified issuer validation before redeeming authorization codes; servers must reject tokens issued for other resources. Proxying a user's unrelated upstream token through an MCP server is prohibited. Discovery URLs and redirects introduce SSRF risks; local stdio server configuration can launch arbitrary programs. State handles must be bound to authenticated principals rather than treated as credentials. These controls must be implemented around the connector, independently of model behavior. [Normative authorization security](https://modelcontextprotocol.io/specification/2026-07-28/basic/authorization/security-considerations), [security implementation guidance](https://modelcontextprotocol.io/docs/2026-07-28/tutorials/security/security_best_practices).

## What OpenClaw actually connects

OpenClaw has two distinct ACP directions. `openclaw acp` exposes a Gateway session to an editor/client; ACP agents launch external harnesses through a backend such as `acpx`. Current docs identify native Codex app-server as the default Codex runtime path, with ACP an explicit alternative. The incoming ACP bridge implements only a subset: per-session MCP server requests and client filesystem/terminal methods are unsupported, and some history/tool presentation is partial. [ACP agents](https://docs.openclaw.ai/tools/acp-agents), [bridge compatibility matrix](https://docs.openclaw.ai/cli/acp#compatibility-matrix).

External ACP harnesses currently execute on the host, outside OpenClaw's sandbox. Sandboxed requesters cannot spawn them, and ACP spawn does not support `sandbox: "require"`. Harness permissions therefore need their own controls. ACPX defaults to approving reads and failing when a required noninteractive permission prompt cannot be shown; these settings are separate from Gateway exec approvals. Its plugin-tools MCP bridge and selected built-in-tools MCP bridge are separately opt-in. [Sandbox boundary](https://docs.openclaw.ai/tools/acp-agents/delivery#sandbox-compatibility), [ACPX setup and permission configuration](https://docs.openclaw.ai/tools/acp-agents-setup).

For coexistence, `openclaw mcp serve` exposes existing routed channel conversations to an external MCP client: transcript reads, live-event polling, replies through stored routes, and approval tools. It starts a stdio bridge connected to the Gateway over WebSocket. Its event queue and observed approvals are live/in-memory; generic clients use polling, while Claude push notifications are client-specific. **Inference:** HyperClaw could potentially consume this bridge without replacing its model runtime, but would acquire consequential channel and approval authority. [MCP conversation bridge](https://docs.openclaw.ai/cli/mcp/serve).

## Skills, plugins, and isolation

OpenClaw follows the Agent Skills `SKILL.md` format. Skill visibility and eligibility are instruction-loading controls, not shell authorization; enabled plugins can contribute skills. Third-party skill content requires review, and tool availability still needs enforcement separately. [Skills format, gating, and security](https://docs.openclaw.ai/tools/skills).

Native OpenClaw plugins load runtime modules **in-process**. Compatible Agent Plugins/Codex/Claude/Cursor bundles map selected content instead: skills, certain commands/hooks, and supported MCP configurations. Some original features are merely detected, including Claude `hooks/hooks.json` and Cursor rules/agents/hooks. Bundles avoid arbitrary in-process runtime modules but can launch MCP subprocesses, so they are not automatically safe. Portable content compatibility does not imply runtime-plugin compatibility with Python. [Native plugin formats](https://docs.openclaw.ai/tools/plugin#understand-plugin-formats), [bundle mappings and security](https://docs.openclaw.ai/plugins/bundles).

OpenClaw labels **all plugin APIs experimental**; ordinary plugins do not thereby require a Labs switch. Native plugin adoption therefore also creates a compatibility-maintenance obligation. [Experimental API status](https://docs.openclaw.ai/concepts/experimental-features).

OpenClaw explicitly supports **one trust boundary per Gateway**: a single operator or mutually trusting team. Session keys route context; they are not authorization tokens. Session tools default to Gateway-wide visibility, and operator roles and exec approvals are collaboration/intent controls. Mutually adversarial users need separate Gateways and preferably separate OS users/hosts. Ownership filters, participant history, and presence in multi-user mode likewise do not isolate users. [Security trust model](https://docs.openclaw.ai/gateway/security/trust-model), [multi-user boundary](https://docs.openclaw.ai/concepts/multi-user).

## HyperClaw adoption decision

HyperClaw declares Python **>=3.11**, with no MCP/ACP SDK in its dependency manifest; its README describes local Ollama routing while acknowledging that tools can independently access external services. [Local manifest](../../pyproject.toml), [provider/tool boundary](../../README.md#configuration-and-local-defaults). Official MCP Python SDK **2.0.0**, released **2026-07-28**, supports the new revision and earlier revisions; its Python minimum is 3.10. Its current roadmap still lists the Tasks extension and some optional auth mechanisms as gaps. ACP also publishes a Python SDK. [MCP release](https://github.com/modelcontextprotocol/python-sdk/releases/tag/v2.0.0), [tagged Python requirement](https://github.com/modelcontextprotocol/python-sdk/blob/v2.0.0/pyproject.toml), [current roadmap](https://github.com/modelcontextprotocol/python-sdk/blob/main/ROADMAP.md), [ACP Python SDK](https://agentclientprotocol.com/libraries/python).

**Engineering judgment:** begin with one allowlisted MCP server, bounded tool/result schemas, explicit credential and egress scope, timeouts/cancellation, and an explicit enforcement boundary around tool dispatch. Evaluate mixed-version peers before claiming interoperability. Keep Ollama model selection independent from connector authorization. Add an ACP adapter only against a specified client/harness capability matrix. Review imported skills and expose unsupported bundle features clearly. Do not treat any protocol, session identifier, working directory, or approval dialog as an OS sandbox or tenant boundary.
