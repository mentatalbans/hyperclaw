## Schedule semantics and review correction

Schedules retain immutable creation payloads for idempotency separately from mutable status, generation and due time. All accepted instants normalize to UTC with fixed microsecond precision. The earliest pending nominal instant remains pending while its session is occupied. When accepted after downtime, a single run represents the coalesced occurrence; the next instant advances along the original cadence strictly beyond the tick time. Occurrence reservation, run, user message, queued event and advancement share the existing Store transaction and connection.

Reset pauses schedules in the same transaction as the generation change. Retarget compares the expected schedule generation with the selected current session generation. Uncertain completion pauses future occurrences in the terminal run transaction and cannot be cleared through retarget. Completed schedules cannot resume. Pausing does not cancel accepted work, and cancelled, failed or interrupted occurrences remain consumed.

The first schedule review reproduced an ordinary v2 run with a later-reserved `schedule:` request ID being adopted as a new occurrence. The correction preserves that historical run and event, chooses a fresh bounded internal ID within the transaction, and defensively rejects scheduled adoption of preexisting runs. The new migration regression failed with `legacy-run` before the fix and passed afterward; covering Store/schedule tests passed 31, affected integrations 30 and unit tests 130. Scoped re-review found the Important issue addressed with no new breakage. Daemon review found the task spec compliant and approved its quality, with no Critical or Important issue. The independent full M3 review of `4727861..dc4083e` found the spec compliant and quality approved, with no Critical or Important finding. It independently matched all six gate summaries and all 53 source/test/dependency hashes to the retained artifacts and current files. It classified two follow-ups as nonblocking: scanning all active schedules before due filtering, and generic maintenance-failure logging without exception detail. Large-population scheduling performance was not benchmarked. The complete final review is retained in the results JSON.
