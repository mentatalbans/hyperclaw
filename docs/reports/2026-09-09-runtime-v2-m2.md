# Runtime v2 M2 acceptance — 2026-09-09

M2 adds controlled file tools and Docker commands to the durable M1 runtime on `refactor/runtime-v2`. Implementation commit: `b11a34c`. Work began at `7fa9dee`; the [implementation plan](../superpowers/plans/2026-09-09-runtime-v2-m2.md) was committed before implementation. M2 is implemented and verified. M3 has not started.

## Shipped behavior

One Executor uses the existing Store connection to record invocation intent, exact approvals, immutable receipts and observed artifacts. Runtime persists full model/tool blocks, pending arguments, repeated-call counts and consumed active time before effects. Waiting approvals release the worker, survive restart and expire after 24 hours. Resume executes the persisted call. Completed or uncertain invocations do not execute again; uncertain runs cannot use the linked-retry operation.

The five admitted tools are workspace read, list, literal search, write and Docker command. File operations use directory descriptors, reject path escapes and unsafe file types, settle even if their caller is cancelled, and verify published bytes. Write and execute authority are separate workspace-scoped grants. An exact command approval without a write grant receives a read-only workspace. Authenticated HTTP and CLI expose workspace identity, grants, approval decisions and receipts; CLI image submission and per-run tool allowlists use the same runtime.

Docker containers have installation/invocation labels and a persisted ID before start. Cancellation verifies stopped state before recording termination; startup reconciles owned containers before queued model work. Containers use an unprivileged UID, read-only root, dropped capabilities, no new privileges, no network, CPU/memory/PID limits and bounded temporary storage/logs/output. Only the selected workspace is mounted. The resolved multi-platform tool image is:

```text
python:3.13.15-slim-bookworm@sha256:ed86c82274b3c69b52fb5820f358f0bd7df0b603332063cb5c6e32bd220c3e6e
```

The model transport retains complete text/thinking/signature/tool blocks and validates split JSON calls. Limits include 12 model rounds, three identical calls, 16 calls per round, 256 content blocks per response, 64 KiB cumulative thinking signatures, 64 KiB tool output, and tool deadlines up to 60 seconds within the remaining run budget. PNG/JPEG/GIF/WebP inputs have validated encoding/type and a default 64 KiB serialized context budget, explicitly raisable to 8 MiB.

## Decisions and review corrections

- The existing design and explicit user request authorized plan execution and commits. Independent backend/workspace/transport tasks shared named interfaces; coupled Store/Runtime integration stayed together.
- Migration retains M1 accepted requests with `tools=[]`, creates a pre-migration backup, and preserves history. An identical no-tools resubmission replays; changing to M2 tool defaults under an old request ID conflicts.
- Active time excludes queue and approval waits. After abrupt death, the running interval is conservatively charged through recovery because the crash instant is unknown. A late restart may exhaust the remaining budget.
- Review found duplicate artifact-check paths and missing recovered-command verification; unique-path validation and one verifier now cover normal completion and reconciliation. Wrong-hash regressions pass.
- Review found the container create/start workspace gap and an unreceipted dispatch rejection. The backend now rechecks workspace identity immediately before and after start; a changed workspace triggers termination and uncertainty, while known dispatch rejection settles a durable receipt before cleanup. Docker's `removing` state is not treated as termination evidence.
- Thinking signatures now have an aggregate UTF-8 byte bound, and empty blocks cannot bypass retention limits. Focused fragmented, multibyte, multi-block and 257th-block regressions pass; independent re-review found no remaining important issue.
- The three M1 live cases explicitly disable tools to preserve their single-request usage assertions; the M2 file-tool case tests actual tool usage separately. The deadline regression allows two seconds for real IO/SQLite scheduling while deliberately withholding model completion; the former 150 ms threshold flaked under simultaneous verification load.
- Temporary implementation commits had cross-commit dependencies. Delivery groups only this session's unshared implementation changes into a self-contained commit; the original plan and all history through `7fa9dee` remain intact, with intermediate history retained at `refs/codex/runtime-v2-m2-implementation-history`.

## Scope and limits

The M2 gates establish the documented controls and recovery behavior. They do not establish exactly-once external effects or absolute Docker isolation. Backend-loss tests inject loss at the backend boundary; they do not stop the shared Docker daemon. Linux verification uses a trusted test runner with access to the Docker socket, while runtime command containers never receive that socket. Non-root Linux daemons use the workspace owner's UID; a root daemon uses UID 65532 and needs a deliberately accessible workspace.

Changes remain on `refactor/runtime-v2`; no push, merge or running-service adoption was performed. Personal roots, `.engram`, the main checkout and existing services were preserved. M3 scheduling and its broader process-kill matrix, M4 memory, M5 MCP/skills and M6 adapters remain unimplemented.
