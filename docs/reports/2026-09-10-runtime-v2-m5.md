## Supported behavior

Skill packages live under the operator's runtime `skills` directory. The supported `SKILL.md` subset has exactly `name` and `description` front matter, followed by nonempty Markdown and explicitly referenced `.md`/`.txt` resources. Package names are bounded lowercase letters, digits and single hyphens. Unsupported hooks, extra metadata, path escapes, links and nonregular files are rejected. External HTTPS references remain text and are never fetched.

The loader bounds the main file and each resource at 16,384 bytes, the combined package at 32,768 bytes, referenced resources at 16, traversal entries at 512 and depth at 16. Admission binds the exact content hash. Submission binds up to four explicitly selected skill hashes; first execution rechecks the package before contacting the model. Checkpointed runs retain their original instruction snapshot, with admission rechecked before further model or tool work. Selected instructions use Ollama's separate system field, count against the context budget and stay out of later unselected conversation history.

The optional `mcp==2.0.0` dependency owns protocol semantics. Actual SDK peers exercise revisions `2026-07-28` and `2025-11-25`: the former uses discovery and protocol-version metadata, the latter initialize/initialized. The client disables caching and retries, including state-only InputRequired retries. Sampling, roots, elicitation, tasks, subscriptions, remote authentication and unsupported result types are outside this integration.

Operator admission binds the documentation content, expected catalog, immutable image, protocol and complete container policy. The snapshot contains at most 512 public text files, 65,536 bytes per file and 8 MiB total, with bounded source traversal. Changing source content, catalog, image, protocol or policy requires renewed admission. Revoking and re-admitting identical content does not revive an older run's authority. Pending approval hashes include the selected MCP admission even for another tool in that run.

Each invocation mounts only its admitted snapshot at `/docs`, read-only. The profile requires UID/GID `65532:65532`, no network, a read-only root, dropped capabilities, no-new-privileges, init, bounded tmpfs/logs, 256 MiB memory, one CPU and 64 PIDs. Creation and inspection consume the same canonical profile that admission fingerprints. No host environment variables, credentials, runtime roots or Docker socket are passed to the peer. The image is pulled or built explicitly by the operator; invocation uses `--pull never`.

Search accepts a nonblank query of at most 256 UTF-8 bytes and a strict limit of 1–5. Read accepts a safe relative public path, positive starting line and at most 200 lines. Results carry source paths, line information and observed full-file hashes. Read excerpts are bounded at 8,192 bytes, search excerpts at 512 bytes, complete serialized results at 65,536 bytes, and wire frames at 262,144 bytes before SDK parsing.

A successful receipt requires a valid bounded result and confirmed peer termination. Lost read results with confirmed termination fail or interrupt; unknown termination remains uncertain. Startup reconciles installation/invocation identities even when current MCP configuration or its optional SDK is absent. Completed receipts never replay, and raw protocol logs never become success evidence.

Admission uses authenticated operator HTTP/CLI administration. [README commands](../../README.md) cover skill inspect/admit/revoke and MCP inspect/admit/revoke; the [example peer guide](../../examples/mcp-docs/README.md) covers the explicit image build and configuration. Ordinary runs activate neither extension automatically.

## Review corrections and limits

The skills task review found that a queued run could read changed package contents before its first context was created, and that several filesystem/count limits lacked meaningful boundary tests. The fix binds submission hashes to the first loaded context; real FIFO, combined-byte, resource-count, entry-count and depth cases cover the limits. Its scoped rereview found both issues addressed.

The MCP task review found that the admission fingerprint covered only part of the Docker sandbox and that actual init was not inspected. A single canonical profile now feeds admission, container creation and inspection. A representative PID-limit change invalidates admission and a pending write-policy hash while holding the admission ID fixed; an inspected container with init disabled is rejected. The scoped rereview confirmed the finding addressed with no new Critical or Important issue, including inspection of the complete 12-case Docker evidence.

The initial Docker image-build attempt encountered Docker Desktop's engine still starting after idle suspension; later readiness and the explicit build succeeded. The normal application activation did not restart or reconfigure shared services. Task-owned finite keepalive containers prevented further idle startup during acceptance. An early cancellation test truncated its own protocol-log marker probe; increasing that existing bounded probe to 65,536 bytes exposed the marker, after which cancellation and the full 12-case MCP Docker gate passed. Earlier attempts remain in the evidence instead of being counted as successes.

The first Linux offline acceptance run had 331 passes, one expected base-only skip and one failure in the queued skill-revocation test. The test submitted a run and immediately revoked its skill without establishing that the run was still queued; the observed run completed successfully first. The corrected test holds a separate gated run in the worker, observes the selected run's queued state, revokes admission, then releases the blocker. It requires failure before any selected-run provider request. This changes test synchronization only; runtime behavior and the peer image remain unchanged. The failed attempt is preserved in `m5-linux-attempt1` evidence.

The first seven-case Qwen attempt passed the six existing scenarios but failed the new documentation case. Saved checkpoint evidence shows that Qwen requested search `limit=10`; the schema already specified a maximum of 5, and the runtime correctly returned `invalid_tool_arguments` before creating an invocation. The capability-test prompt now states the allowed search limit and requests reads of at most 80 lines. It still supplies neither the answer nor the opaque marker. No runtime validation, image, SDK retry behavior or authority was relaxed. This demonstrates a bounded capability when the model follows the tool contract, not guaranteed compliance with arbitrary prompts.

Ruling: M5 MCP tools are limited to directly submitted runs, including detached runs. Schedule creation rejects them because the existing scheduler cannot bind the new admission/revocation authority safely. Cost if wrong: scheduled documentation work needs a later admission-binding extension. Existing scheduled tool choices are preserved.

M4's nonblocking follow-ups remain: the duplicated receipt-output ceiling, an inherited eight-second Docker recovery fixture, generic maintenance error causes, and unbenchmarked active-schedule population performance. Hosted CI is configured but has not been executed. This milestone adds no automatic service adoption or legacy data import.

Final whole-M5 review found two Important issues and no Critical or Minor issue. First, replacing a stat-checked regular skill file with a FIFO before its blocking open could stop the event loop. Nonblocking opens now let the existing descriptor checks reject that replacement. Two bounded public regressions replace the main file and a resource, require HTTP 422, and verify health, cancellation and subsequent unselected work.

Second, valid maximum-size packages with long resource paths could render 145,366 instruction bytes, exceeding the old 139,264-byte checkpoint cap after submission accepted the run. The shared `skill_format.py` renderer now derives a 202,314-byte ceiling from four packages' content, referenced paths, metadata and exact formatting. Submission and checkpoint validation use the same UTF-8 bound. Supported package limits are unchanged; a 145,400-byte context is rejected before acceptance for the measured 145,401-byte requirement, while 262,144 succeeds with exact context provenance and continued daemon health. General worker exceptions are not masked. The consolidated fix and its RED/GREEN evidence are archived. One scoped rereview cleared both findings with no new issues; the complete acceptance sequence then passed against the corrected source.

Cleanup checked 22 recorded disposable roots: nine were removed and thirteen were already absent. All five recorded Linux runner containers had removed themselves; the exact owned keepalive was removed, and no installation-labelled or M5-named container remained. Review reports and the single controller ruling are archived before removal of this milestone's SDD scratch. The local branch, worktree, development environment, reviewed images and local evidence are retained. The main checkout's preexisting `.engram/` and the separate provider-recovery worktree remained unchanged. M6 has not started; no push, merge or shared-service adoption was performed.
